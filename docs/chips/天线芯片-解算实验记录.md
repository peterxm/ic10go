# 交易天线芯片 · 解算方案实验记录（v2 / v3 / v3b / v4）

目标：找出比 v2 更好的「对准解算」方法，并记录编译器侧可改进点。

## 一、解算方案对比（真机实测）

| 版本 | 思路 | 观测量 | 真机结果 |
|---|---|---|---|
| **v2** | 3 点梯度：基准 + 两正交探测 → `atan2` 求梯度方向 → 按 `S0` 走一步 | `SignalStrength` | ✅ **可用**：锁定→转向→3点测量→审问 `InterrogationProgress 0→1`→`Activate` 放行→复位 |
| v3 | 每轴对称 3 点**抛物线峰拟合** `Δ=d(S₋−S₊)/(2(S₋+S₊−2S₀))` | `SignalStrength` | ❌ 实测 H 剖面在 `H≈343` 是**极小值**（非单峰），拟合前提不成立 |
| v3b | 同 v3，但观测量换成 `WattsReachingContact` | `WattsReachingContact` | ❌ 波束外该值为 `-1`，拟合取到 `-1` 就算出乱偏移 → 天线漂走 |
| v4 | **保守爬山**：每轴 ±step 探测，只在目标严格变大且有效时才移动，步长减半收敛 | `WattsReachingContact` | ❌ 探测会把天线挪出波束（`W=-1`），恢复不回来 → 卡死在波束外 |

### 关键观测（真机）
1. **天线有现成的“对准度”量**：`WattsReachingContact`（随对准角度平滑变化），门槛 `MinimumWattsToContact`。
   对准时实测 `WattsReachingContact=1996 ≫ MinimumWattsToContact=199` → **`W ≥ MinW` 是“对准够了”的判据**。
2. `SignalStrength` vs 角度在某些切面**不是单峰**（V=54 时 H≈343 是极小）→ 不能假设单峰。
3. **失败共性**：天线**波束窄、转动慢**（中型 ~1.9°/s），任何“先探 ±step 再决定”的策略，一旦探出波束（`-1`）就回不来。

### 结论
- **v2 仍是最稳的可用版**（结构化，126 行）。
- 更好的解算若要成立，需要：
  - 以 `WattsReachingContact` 为量，但**只在当前点有效时做极小步（≤1°）试探**，且**每步都能回退**；或
  - 直接利用“`W ≥ MinW` 即对准”做**粗定位后停**，不做刻意找峰。

## 二、编译器侧发现

### 1. 关系推理缺口（“非负值传播”）
v4 原版 `wp >= 0 && wp > w0` 在 IR 里降成 `sgez/sgt/min/beqz`（4 条）。其实前面已 `if w0 < 0 { continue }`，故 `w0 ≥ 0`，而 `wp > w0` 已隐含 `wp ≥ 0`。
→ **可去掉 `wp >= 0`**（`climb` 67→57 行，v4 133→124 行）。但这不是简单 peephole，需要**范围 + 关系推理**（`x > y` 且 `y ≥ 0` ⟹ `x ≥ 0`），是一套独立的分析 pass。**本轮未实现**。

### 2. 辅助函数“重复内联”
写一个辅助 `probeRel()`（内部调 `waitloop()`）后，产物里 `waitloop` 变成 **70 行**（正常 37）——被重复内联。
**根因**：被 `outline` 的函数**强制内联**它的被调函数（`internal/lower/outline.go` 注释、`computeLabeledFuncs`）。因为 IC10 **只有一个 `ra`**，编译器不支持嵌套 `jal`（否则内层返回地址会覆盖外层）。
→ 于是同一个共享被调函数（`waitloop`）被多个 outline 函数各内联一份。
**修复方向**：支持**嵌套调用**——进入被调前把 `ra` 存栈、返回前恢复（`push ra; jal; pop ra`），或为嵌套层保留返回地址寄存器。这是**新特性**，不是小改。

## 三、结论与下一步
- 落地：**v2**（chip1 126 + chip2 115），真机验证通过。
- 实验版保留（未采用）：`housing1.peakfit.icg`(v3)、`housing1.peakfitW.icg`(v3b)、`housing1.climb.icg`(v4，124 行)。
- 编译器待做（按性价比）：
  1. **嵌套调用支持**（消除共享函数的重复内联）——收益面广，中等工作量。
  2. **范围/关系推理 pass**（非负值/比较蕴含化简）——收益面广，较大工作量，需全量语料回归 + 差分测试。
  3. 观测量/解算：若再试 v5，按“单轴极小步 + 必可回退 + `W ≥ MinW` 停”设计。

## 四、嵌套调用支持：进展与结论（本轮）

### 已确认（真机）
**`push ra` / `pop ra` 游戏汇编器接受，且嵌套返回正确**。
手写测试（A CHIP）：`main → jal mid → mid(push ra; jal leaf; pop ra) → leaf`，
结果 `d0.Setting = 0+100+10+1 = 111`，`Error=0`。→ 返回地址可正确保存/恢复。

### 已尝试（编译层，**有 bug 已回退**）
在 `internal/codegen/codegen.go` 里：`b.Func != ""` 的块内的 `Call`/`BrCall` 前后发
`push ra` / `pop ra`（在 `Return` 块开头恢复）。

- **编译/测试**：产物确实出现 `push ra; jal; pop ra`，`go test ./pkg/ic10` 全绿。
- **真机**：**`Error=1`**。原因：`ir.Block.Func` **不是可靠的"在 outline 体内"判据**——
  当一个函数（如 `g`）被内联进 `main` 后，它的块仍带 `Func="g"`，于是在 `main` 的调用外
  也插了 `push ra`/`pop ra`，`ra` 处理错乱。
- 结论：**已回退**（不留半成品在代码生成里）。

### 正确的下一步
不要用 `Block.Func`；要在 **lowering/outline 阶段显式标记"哪些 Call 是真正的嵌套调用"**
（例如给 `ir.Call`/`BrCall` 加一个 `Nested bool`，由 `OutlinedFunc` 的调用路径设置），
只对这些调用发 `push ra`/`pop ra`。然后再全量回归 + 差分 + 真机。

## 五、范围/关系推理 pass（`nonnegFold`）

实现了 `internal/opt/nonnegFold`：从分支守卫（`if x < 0 { ... }`、`x >= 0` 等）推导「寄存器 ≥ 0」的 must 事实（跨块数据流），据此
- 把已知非负的 `x >= 0` / `x < 0` 比较折成常量；
- 把 `min(Cmp{Ge,x,0}, Cmp{Gt,x,y})`（即 `x >= 0 && x > y`）在 `y ≥ 0` 时折成后者（去掉冗余 `sgez`）。

**验证**：
- 简单样例（`nn.icg`）确认生效：`sgez`（`wp>=0`）被删。
- `go test ./pkg/ic10 ./internal/opt` 全绿；语料回归 **变长 0 / 变短 0 / 相同 121**。
- ⚠️ **限制**：`housing1.climb.icg` 里 `if wp >= 0 && wp > w0` 这种**在循环体、守卫与 `&&` 相隔较多指令**的形态**未被折叠**（`nonnegFold` 触发了但没命中该骨架）——需进一步排查（可能要在 `fuseBranches` 之前跑，或匹配分支化后的形态）。
