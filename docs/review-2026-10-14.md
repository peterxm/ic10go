## 总体结论

工程质量整体**很高**：测试密度大、`go build`/`go test`/`go vet` 全绿、无 TODO/FIXME 残留、真机验证记录完备、协议错误码体系（`bad-request`/`no-chip`/…）设计稳定。`--diff` 全链路（编译 → 真机 → VM 对拍）经 24/24 场景验证可用。

问题集中在三条主线（第 1 条为游戏源码终审后新增，**严重度最高**）：

1. **数据段缺少真机回归覆盖，且 `--dynamic-stack` 满载边界静默出砖**（§2.9-G4）：默认（正数槽）布局真机端到端**实测可用**（100 项表 + loader 分块，LED=350 ✓）——但 `testdata/bench/ingame/` 里带 `data.loaders` 的场景为 **0 个**，等于招牌特性从未进过真机回归网；而 `--dynamic-stack` 允许 512 项表（+1 哨兵 = 513 槽）通过，哨兵槽被算成**非法的 `-1`**，产出的 loader/runtime 首行 `put db -1`/`get r0 db -1` 在当前游戏上直接停机钉死（反编译 + 真机双确认）。
2. **NaN / ±Inf 的全栈语义不统一**（编译器折叠、优化器比较、内置 VM、真机、JSON 协议各说各话）——它同时是唯一的编译器挂死 bug、一批差分假阳性的根因，以及一次**真机事故**（见 §2.3）的源头。
3. **mod 主线程同步长操作的"永久卡死"家族**——设计文档（docs/ingame-testbench.md §9.5）已点名，但实现不完整，本次真机实测命中。

### 1.2 8 个首轮失败的根因：**接线漂移，非编译器回归**

这 8 个场景都要求 A CHIP **d3 = ElectronicsPrinter**（栈指令 `putd/getd/clrById`、`On` 读写、`s61-s64` 的 expect 含 `d3.On`）。存档里 d3 实际是"逻辑内存 B"（id 705，`On` 不可读、`stack` 无意义），表现为难以归因的错误：

```
✗ both hot -> 1/1: unknown-logic: On is not readable on this device
✗ put 123, read, clear -> 123000  d0.Setting: want 123000, got -6     ← LogicMemory 栈槽返回 NaN，-6 是 NaN 经 JSON 往返后的值
```

失败场景的 VM 差分侧**全部通过**——证明编译器无回归，是测试台存档与场景预期不一致。

> **附注**：`got -6` 与 `unknown-logic` 都是"接错设备后的行为面"：假 mod 复现证明 `putd/getd/clrById` 打在 LogicMemory 上不报错、只是语义完全不同（栈槽=内存单元），返回哪个值取决于设备状态——**这类"值错了"的失败比直接报错更危险**，归因成本高。另外 NaN 经协议往返会碎成各种形态（见 §2.2 P1）。修复接线后 24/24。

### 1.3 真机 review 过程中发生的一次事故（重要）

`s65_ireg.json` 的 "bad id: LED keeps value" case **故意**让芯片执行 `s 1234567 Channel1`（无效 ReferenceId 写通道）。游戏把该线判错后 **PC 钉死在出错行、每 tick 重试**（即 `docs/ingame-test-plan.md` §4.1 记录的"错误态 PC 钉线不推进、重跑有副作用"）。而 mod 的 `push` **在主线程同步跑 loader**（`BenchServer.cs:139-143`，注释承认"may tick"）→ 恰好在这条死循环线上耗 128×N ticks，**游戏主线程冻结、7800 端口全部连接失效、`world.state` 都拿不到响应**，只能杀进程重载存档（存档无损，每 5 分钟自动保存）。`s65` 其余 case（VM 侧全过）在事故后未复跑，建议下次连同 `--diff` 补验。

这正是 docs/ingame-testbench.md §9.5 已登记风险（loader 同步执行、无超时）的一次真实命中。**该 case 应改为不产生死循环的变体，或 mod loader 改异步 drain**（见 §4 改进项 3/4）。

### 2.9.2 测试层缺陷（本轮多条“真机已确认”为何带病存活）
1. **mod/CLI 显示层把非有限值脱敏成 `0`/`null`**（`Num()` NaN→null、typed 解码 null→0、`+Inf`→显示 0）：本轮 `r1=pinf` 被显示成 0，逼出 `sgn` oracle 才看到真值——文档里多条“pinf 回读 0 / 真机 -nan”类“已确认”条目其实是**这个显示层的产物**（F10/B21 的同一机制在误导人工测试）。改进：oracle 化测试（把非有限值经 `sgn/绝对值/比较` 转成 0/1 再观测）+ 协议保留 NaN/Inf 编码。
2. **“已在真机确认”清单没有可重放的场景支撑**：div-by-zero 条目（错的）从未有回归场景；数据段（招牌特性）在 `testdata/bench/ingame/` **0 覆盖**（s27/s63/s64 的 `data.loaders` 全为 0）——G4 这类游戏版本行为变更没有任何自动化能接住。改进：把 §2.9 的六个探针固化为 `s70_datasegment` / `s71_ieee` / `s72_clr` / `s73_qnan` 真机场景（本轮脚本已验证可行，直接改写即可）。

## 4. 改进建议（按优先级）

### P0（安全/正确性）
0. **堵数据段两个洞**（§2.9-G4 / C5）：a) `sema.assignData`/`data.go` 增加容量守卫——`base < 0`（含 `--dynamic-stack`）编译期报错，错误信息对齐 `--user-stack` 路径；b) 场景 runner 白名单放行 `--dynamic-stack/--user-stack/--spill` 等 build 参数（`cmd/ic10c/testbench.go:1955` `benchOptions`），并新增 `s70_datasegment_*` 真机场景（`data.loaders` 非空 + ≥2 段 loader + 版本哨兵负例），让招牌特性进回归网。
1. **全栈统一 NaN/±Inf，方向以游戏源码终审为准（纯 IEEE）**：
   - 浮点比较一律 `math.Float64bits`（`constEqual` C1、`opt.go:1111,2816`）；
   - 优化器定点加**迭代上限**（如 200）+ 超限告警（兜底任何未预见的振荡）；
   - 除零折叠统一为 **IEEE**（`x/0→±Inf`、`0/0→NaN`、`x%0→NaN`）并必带警告（终审 §2.9-G1：lower 现有 `x/0→NaN` 是**双重错误**——值错 + 生成 G2 停机毒代码）；`nan` **字面量**在取值点真机会停机（§2.9-G2），产物里出现裸 `nan` token 写设备 = 砖机代码，编译器应仅在运行时路径（`div x x x` 式）产生 NaN；**spec §8.6 与 `target-ic10.md:420-422` 的“已真机确认”条目需按 §2.9 勘误**；
   - 协议文档（§4）增加 NaN/±Inf 编码约定（建议字符串 `"nan"/"pinf"/"ninf"` 或显式 `null`+类型），C# 侧统一 `"R"`/不变文化格式（P1/P2/P3）。
2. **mod 防冻结**（B1/B18）：loader 全部改异步 drain（复用 `run` 的队列机制）+ 超时 + `push` 完成后验证 loader 行数跑完（B14 的 128 tick 硬编码一并解决）；`watch`/广播写出站队列 + `SendTimeout`，**任何 socket 写不进主线程锁**；Go 客户端加默认读超时。
3. **harness 结果可信性三连**（全部是"绿色谎言"级）：`push` 的 `compileError` 必须让 `run`/`benchPush` 硬失败（B17，最简：`res.Error != nil → exit 2`）；`run`/`step` 返回的芯片错误必须接收并上报（B22）；`run` 前必须核对实际 `paused`（B23）。
4. **字面量/语句校验补洞**（C2/C3/M1/M2）：lexer 拒 `0b` 后非 0/1、缺指数位、溢出值报错而非归零；非调用表达式语句报 "statement has no effect"；`use … on conn` 数字严格解析；switch 重复 default 报错。

### P1（高价值）
5. **场景接线预检**：`testbench run` 在第一个 case 前比对 `state.devices[].prefab` 与场景 `ports` 声明，不匹配即清晰报错停（本轮 8 连败若早有此检查，10 秒定位）。review 侧已有**可运行原型**（`internal/testbench/preflight.go` 思路 ~120 行 + 9 例匹配器表 + 正/负对照测试，验证于 scratch copy）：role 别名表（`LED→*Display`、`Memory→*Memory`、`ElectronicsPrinter/Autolathe`）保持场景文件零改动；设备缺席报"nothing is on the port"；`--allow-rig-drift` 逃生门。再进一步：`ic10c testbench verify-rig` + 仓内 golden `rig.json`（从 `CanLogicRead/Writable` 免费得到每设备的 reads/writes 能力表，`run.sh` 开头一条 exit 2 门），把本轮踩到的两类晚期失败（`On is not readable`、`Setting is not writable`）在 0.1 秒内点名。
6. **芯片选择改连接级会话**（B19）：`--chip` 不再改写全局默认；被 pin 芯片消失 → `no-chip`，禁止静默回退。配合**复合 `case` 命令**（一次主线程动作内完成 `writes→ticks→reads→registers`，返回一个原子快照）：`set→run→get→state` 4 次往返合 1，中间重绑/并发观察在结构上不可能发生，3-case 场景从 ~13 次调用降到 ~5。
7. **`s65_ireg.json` 的 "bad id" case 改造**：它触发的是**游戏未定义行为**（PC 钉死 + 每 tick 重复写），真机上把 mod 主线程拖死——建议改用"读失败但不死循环"的形式，或在场景 schema 支持 `expectError`（断言 `errors.code` 非空即通过，跑完立刻 reset），并让 loader 每轮加"PC 是否推进"看门狗（与 B1 同一机制）。
8. **`--diff` 补齐承诺**（B24 + B15）：VM 侧评估 `expectReg`、统一 `closeEnough`、`m.Strict` 开启未接线即报错、逻辑名 canonical 化（`builtin.LogicTypeNames`）、写入序列对比接回（`writes` 基线管道都在，注释未接）、diff 失败计入退出码并进 `--json`。这是 README 宣传的"回归安全网"本体。
9. **`--redundant-device-writes`/`--hoist-device-writes` 的 guard 收紧**（§2.6 两个实测误优化）+ 文档如实降级；为两 flag 各补 2 个真机场景。
10. **VM 错误态与 Special 语义**（V1/V2/V3/V5）：`div/mod` 0→NaN、`l pinf/ninf/nan` 进寄存器→芯片错误+钉线、`clr` no-op——让 VM 能复现"游戏挂起"这类行为，diff 才有资格当安全网。
11. **超时架构**（B31/F7 类）：按命令分级 deadline（`ping/state` 5s，`run/trace` 无界但回报进度）；>1s 的长命令走 `{job}` + `job.poll`；客户端 `CallCtx(ctx)`（现在 `Call` 无 context，Ctrl+C 救不了 CLI）。
12. **协议对账测试化**：docs §4.2 的表（命令/参数/错误码）做成生成物（`docs/protocol.json` + golden test 断言 C# `Execute` switch 与 Go 错误码集合），B30/B31 类"文档承诺未实现"漂移即可在 CI 抓到；把 scratch 的**假 mod 集成 harness**（本轮 B17/B20/B21/B23 均由它复现）收编进 `internal/testbench` 测试——这些路径没有真游戏也能测。
